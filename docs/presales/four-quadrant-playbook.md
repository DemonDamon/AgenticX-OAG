## 一、开场白模板（四问引导词）

> 使用场景：会议开始 10 分钟内，客户说完「我们想建本体 / 知识图谱 / Agent 平台」之后。

「今天第一次交流，我们先不谈产品，也不给您讲方案。我准备了**四个问题**，帮您把这个诉求拆清楚——因为『本体』这个词底下，其实压着**四种完全不同的东西**：Semantic Ontology、知识图谱 Schema、Palantir 式执行层、Agent 治理层。它们的核心命题、技术栈、工程哲学全都不一样，**选错一种，后面的预算全打水漂**。所以先花五分钟做一次定位，比后面聊三小时都有用。
>
> 四个问题都只需要回答『是』或『否』：
>
> **Q1：您需要逻辑推理吗？**——就是从已知推导未知：概念层级自动传递、配置项互斥依赖自动检测这类。
>
> **Q2：您需要多跳关联查询吗？**——实体之间隔着两跳以上的间接关联，比如人—账户—设备—地址连出来的隐式团伙。
>
> **Q3：您需要操作执行闭环吗？**——让系统真的去改业务对象的状态，而且要审批、要回滚。
>
> **Q4：您需要约束 Agent 行为吗？**——Agent 能调哪些工具、什么动作必须拦下来、事后能不能审计。
>
> 哪个问题您答『是』，我们就先聊哪个方向；四个都『否』，默认从治理层谈起。」

**引导技巧：**

- 客户答「是」的瞬间就停，不要继续问后面的问题——决策树是逐层排除，命中即终止。
- 客户说「我们全都要」：不争论，回一句「全都要没问题，但**顺序**很重要——我们先定位最痛的那一个，POC 只主打一个象限，验证价值后再叠加。这正是紫皮书的演进原则：**组合是演进而来的，不是设计出来的**。」然后继续追问「如果只能保留一个，是哪个？」
- 客户答不出来：换到 16 场景匹配表，让客户「对号入座」——「这张表是紫皮书里 16 个典型场景的推荐选型，您看看哪一行最像您的情况？」

## 二、每象限 3 分钟讲解稿

### 2.1 Semantic Ontology（知识层）——世界是什么

> 触发条件：Q1 答「是」。

「您命中的是第一种，叫 **Semantic Ontology**，语义本体论。它回答的问题是『**世界是什么**』——用形式化逻辑定义概念的本质与边界。技术栈是 OWL 公理、RDF 三元组，跑在 HermiT、Pellet 这类推理引擎上，查询走 SPARQL，存在 Stardog、GraphDB 这类三元组存储里。它的哲学根基是**开放世界假设**：没声明的东西不是『不存在』，只是『还不确定』——所以它能推理出『X 是 Y 的子类、Y 是 Z 的子类，所以 X 是 Z 的子类』这种**图里没显式存、逻辑上必然成立**的关系。

坦率讲，**这个象限我们不自研**——推理引擎是二十年以上的学术积累加标准生态，自研没有胜算，也没有必要。我们的做法是留**标准的 RDF 导入/导出接口**：您需要推理的部分，我们对接 HermiT/Pellet 类生态伙伴；推理出来的隐含三元组，可以物化进我们的图谱层做高性能查询。所以这一象限的 POC 形态是**转生态合作**——我们出接口和集成，推理引擎出推理。

一句话收尾：**您要的是『逻辑上对不对』，这个交给推理生态；我们负责让推理结果在业务系统里『查得快、用得上』。**」

### 2.2 KG Schema（查询层）——实体之间怎么连

> 触发条件：Q2 答「是」。

「您命中的是第二种，**KG Schema**，知识图谱模式。它回答的问题是『**实体之间怎么连**』——用图结构表达关联拓扑。技术栈是属性图：节点、边、属性，查询用 Cypher、Gremlin、GQL，图算法做 centrality、社区发现、最短路径，存在 Neo4j、NebulaGraph、TigerGraph 这类图数据库里。它的核心计算原语是**遍历**——从实体 A 出发，经过 N 跳，能到哪些实体。注意：遍历不产生新知识，只是对已有边的组合查询，所以它**快**，而且结果确定——这是封闭世界假设，图里没有的边就是不存在，否定查询语义清晰。

**这是我们自建的象限**：复用 AgenticX 的 knowledge/graphers 能力，CWA 与 PG+AGE（PostgreSQL + Apache AGE）的技术选型天然匹配——您可以复用现有 PostgreSQL 运维体系，不用新引入一套图数据库。典型场景您可以对号入座：反欺诈团伙关联、企业知识图谱、航线网络优化，都是多跳路径发现。

POC 形态是**检索型**：选一个多跳关联场景，跑通『提问 → 检索 → 答案 + 来源追溯』全链路，用 faithfulness、citation 准确率、幻觉率三个指标跟您现在的纯 RAG 做对照。

一句话收尾：**向量检索给您的是『相似』，图谱给您的是『关联』——隔着两跳以上的隐式关系，只有图谱查得出来。**」

### 2.3 Palantir Ontology（执行层）——业务怎么运转

> 触发条件：Q3 答「是」。

「您命中的是第三种，**Palantir 式的执行层 Ontology**。它回答的问题是『**业务怎么运转**』——用对象加动作驱动操作闭环。技术栈长这样：数据层把人、设备、订单映射成**强类型的 Object 和 Link**；动作层在对象上定义 **Action 和 Function**，带状态迁移、审批流、事务；应用层是 Workshop、AIP、OSDK 这类操作决策界面。它的核心计算原语是**执行**——执行这个 Action 之后，对象状态怎么变。执行是真实的世界改变，所以必须事务保证、必须能回滚。

**这是我们的核心对标象限，也是最值钱的部分**：Action Gateway + Function + Writeback。Palantir 用这套东西在航空、供应链、金融做了二十年验证；我们做的是更轻、更 Agent 导向的版本。16 场景表里『运行控制决策』『供应链调度』『订单全流程管理』都落在这个象限。

POC 形态是**操作闭环型**：选一个 Action 真实改变业务对象状态的流程——必须带审批或回滚——跑通 Object → Action → Writeback 闭环，验证状态一致性和可回滚性。

一句话收尾：**前两种本体『描述世界』，这一种『驱动世界运转』——客户真正付费的，从来是让系统替业务干活。**」

### 2.4 Agent Ontology（治理层）——Agent 该怎么做

> 触发条件：Q4 答「是」，或四问全「否」（默认兜底）。

「您命中的是第四种，**Agent Ontology**，智能体本体论，我们叫治理层。它回答的问题是『**Agent 该怎么做**』——用约束规约智能体的行为边界。技术栈：工具层用 Tool Schema 定义 Agent 能调什么（MCP、Function Calling）；治理层是 Guardrail 加 Policy——输入过滤、工具限权、输出审查；约束层是规则加白名单，全程审计留痕。它的核心计算原语是**约束**——Agent 即将执行的动作，允不允许？约束是运行时拦截，不产生新知识、不改变世界状态，在动作发生前做合规判定。

**这是我们的核心差异化**：治理 LLM 决策过程本身。这个位置目前是空档——Semantica 没有这个能力，Palantir AIP 不外售。大模型 Agent 越自主，这一层越值钱：没有治理的 Agent 上生产，等于把权限敞口交给概率系统。16 场景表里投顾 Agent、维修工单、用药辅助、代码生成、智能客服全在这个象限。

POC 形态是**治理型**：拿一个高危场景——退款、派工、用药——跑通『Agent 调用 Action 前先过约束校验，允许或拒绝，全程留痕』，用拦截正确率和审计完备性说话。

一句话收尾：**别人卖 Agent 大脑，我们卖 Agent 的行为边界——企业敢把 Agent 放进生产环境的唯一理由。**

**（四问全否的兜底话术）**「四个都不是？那正好说明您现在最缺的不是某一个能力，而是**治理框架**——从治理层起步成本最低、见效最快，而且后面不管加哪个象限，治理层都在。我们就从治理型 POC 谈起。」

## 三、组合演进路径图

> 原则（紫皮书 8.4 误区四）：**组合是演进而来的，不是设计出来的。** 先用决策树选定一个核心本体论，验证价值后再逐步叠加其他层；禁止一上来推三层全栈。

```text
第一步 · POC（2~4 周，只打一个象限）
    ├─ Q1 命中 → Semantic Ontology（知识层）→ 转生态合作，不出 POC 主战场
    ├─ Q2 命中 → KG Schema（查询层）        → 检索型 POC
    ├─ Q3 命中 → Palantir 式执行层           → 操作闭环型 POC
    └─ Q4 命中 / 四问全否 → Agent 治理层     → 治理型 POC
                        │
                        │  验证价值（faithfulness / 闭环一致率 / 拦截正确率）
                        ▼
第二步 · 叠加第二层（按客户实际痛点，演进而非设计）
    KG Schema ──映射──▶ Palantir 式执行层        模式二：数据层 + 执行层
      （关联发现）          （操作闭环）          KG 发现风险关联 → 触发处置 Action
    Palantir 式执行层 ──拦截──▶ Agent 治理层     模式三：业务层 + 治理层
      （做什么）              （能不能做）       Agent 调 Action 前先过 Guardrail 校验
                        │
                        │  再次验证
                        ▼
第三步 · 全栈组合（理想形态，紫皮书 8.3）
    Semantic ──▶ KG Schema ──▶ Palantir Ont. ──▶ Agent Ont.
   （知识层*）     （查询层）      （执行层）        （治理层）
    * 知识层走 RDF 接口 + 生态合作，不自研；模式一（知识层+查询层）按需物化接入
```

**三条演进路径的售前口径：**

| 路径 | 适用客户 | 话术要点 |
| --- | --- | --- |
| 检索型 → 操作闭环（模式二） | 已有/先做图谱的客户 | 「图谱查出风险关联只是第一步，值钱的是**触发处置动作**——这就是我们检索 → Action Gateway 闭环。」 |
| 操作闭环 → 治理层（模式三） | 已上 Agent/AIP 的客户 | 「Agent 每次调 Action 前先过约束校验（能不能做）——业务层管做什么，治理层管能不能做。」 |
| 治理层 → 操作闭环（模式三逆推） | 先被 Agent 风险逼着上治理的客户 | 「治理层有了白名单和审计，自然需要被治理的动作是强类型的——执行层的 Object + Action 是治理的前提。」 |

## 四、四大红线应答话术

> 红线含义：出现以下四类诉求时，宁可放慢节奏，不要顺着客户把方案做歪。正文口径来自紫皮书 8.4。

### 红线一：客户想用知识图谱替代一切

**误区原文**：试图用知识图谱同时做概念推理、操作执行和 Agent 约束。图遍历无法替代逻辑推理（缺传递性推导），图节点无法承载 Action 状态机，图属性无法定义行为约束。图谱只是四种本体论中的一种，不是万能替代品。

**应答话术**：
「图谱方向没问题——关联数据确实该进图谱。但您刚才提到的三件事：术语层级**推理**、操作**闭环**、Agent **管控**，分别对应另外三种本体能力，图谱一件都替不了。我们先用四问定位最痛的那一个——POC 只主打一个象限，验证价值后再按组合模式叠加。**把宝押在一个象限上做深，比四件事都做半吊子强。**」

### 红线二：客户混淆概念层级与实例关联

**误区原文**：把『飞机是一种航空器』（概念间子类关系，Semantic 的 TBox）和『航班 CA123 使用飞机 B-1234』（实例间关联，KG Schema 的边）塞进同一个图模型——概念推理和实例查询互相干扰，图规模膨胀且无法做有效逻辑推理。正确做法：概念层用 OWL 本体，实例层用图数据库，物化或映射桥接。

**应答话术**：
「这是两类东西：『飞机是一种航空器』是**概念间的子类关系**，归推理管；『CA123 使用 B-1234』是**实例间的关联**，归图数据库管。混在一张图里，两边都做不好——推理做不动，查询还膨胀。正确姿势是分层：概念层用本体，实例层用图数据库，中间用物化或映射桥接。**这正是组合模式一的标准做法，我们按这个分层帮您建。**」

### 红线三：客户忽视世界假设的后果

**误区原文**：在开放世界假设（OWA）系统上做否定查询（『找出没有维修记录的飞机』），或在封闭世界假设（CWA）系统上期望推理完备性。前者会遗漏数据（OWA 下『没有记录』≠『没有维修』），后者会错误认为『图中没有就是不存在』。正确做法：选型时明确标注系统的世界假设，查询语义与世界假设匹配。

**应答话术**：
「这个问题先问一句：您的系统是开放世界还是封闭世界？如果是开放世界，『没查到维修记录』不等于『没有维修』——否定查询会漏数据。我们的查询、执行、治理三层都是**封闭世界**：图谱外即不存在、未定义的 Action 就是不执行、未授权的工具就是不能调——结果确定、边界清晰。如果您的场景必须开放世界推理，那是 Q1 的事，走 RDF 接口接生态推理引擎，我们不硬做。」

### 红线四：客户要求一步到位搭四层全栈

**误区原文**：看到『全栈组合』的理想形态后，试图一步到位搭建四层架构。在没有验证单一本体论价值前就搭建组合系统，会导致架构复杂度失控、团队认知负荷过重、每一层都做不好。组合是演进而来的，不是设计出来的。

**应答话术**：
「全栈是**终点形态**，不是起点。没有验证单一象限的价值就上四层，架构复杂度失控、团队认知过载、每一层都做不好——紫皮书把这列为四大误区之一。我们的建议：先用决策树选定一个核心象限做 POC，两到四周，验证价值后再按实际痛点叠加第二层。**组合是长出来的，不是画出来的**——三种组合模式全都是这么演进的，我们的落地路线图也是这么设计的。」

## 五、常见客户异议 Q&A（10 条）

**Q1：「我们已经建了知识图谱 / 买了图数据库，还要你们干什么？」**
A：先确认图谱解决了什么——按决策树，图谱回答的是 Q2（多跳关联）。Q3 的操作闭环（Action 改状态、审批、回滚）和 Q4 的 Agent 治理（权限、审计）是图数据库本身给不了的。而且我们的 KG Schema 走 PG+AGE，可以直接长在您现有数据体系上。建议：拿一个「图谱查出来了、但人工处置慢」的环节做操作闭环型 POC。

**Q2：「RAG + 向量库已经够用了，为什么还要本体？」**
A：向量检索给的是「相似」，不是「关联」和「约束」。隔两跳以上的隐式团伙关联（Q2）、要审批回滚的状态流转（Q3）、Agent 的权限边界（Q4），向量库都无能为力。如果您的场景就是单文档问答，纯 RAG 够用，我们不建议您上本体——先用四问过一遍，别为用不上的能力付费。

**Q3：「直接上大模型 Agent 不就行了？为什么还要治理层？」**
A：Agent 越自主，越需要边界。Q4 治理层做三件事：工具白名单（只能调什么）、运行时拦截（调用前校验允不允许）、全程审计（事后可追溯）。没有治理的 Agent 上生产，等于把业务操作权限交给一个概率系统。这正是 Semantica 没有、Palantir AIP 不外售的能力位。

**Q4：「你们和 Palantir 什么区别？」**
A：能力位上，我们对标 Palantir Ontology 的执行层（Object + Action + Writeback），这是最值钱的部分；差异在三处：更轻（不用整仓 Foundry）、更 Agent 导向（原生面向 LLM Agent 的 Action Gateway）、以及治理层是 Palantir AIP 不外售的空档。另外我们不锁生态——RDF 标准接口、PG+AGE 存储，客户资产可迁出。

**Q5：「能不能四层一步到位？」**
A：不能，这是红线四。组合是演进而来的，不是设计出来的——先单象限 POC（2~4 周），验证价值再叠加。一步到位的结果是复杂度失控、每层都做不好。我们宁可第一单小，也要每一层都立得住。

**Q6：「POC 要多久？我们要投入什么？」**
A：2~4 周。我们出 1~2 个工程师 + 1 个行业顾问；客户侧要三样东西：一个具体场景（如反洗钱、供应链风险、设备故障诊断）、真实或脱敏样本数据、每次周会 30 分钟的业务专家时间。交付物：可演示的场景 Demo、评测报告（vs 纯 RAG / vs 纯 Agent）、场景本体模型（YAML）、四象定位报告（含后续组合演进路径）。

**Q7：「我们没有知识工程师，本体建模是不是很重？」**
A：POC 阶段用轻量本体：10~20 个对象类型，手工加 LLM 辅助，我们带建。重本体（上百类、OWL 公理级）是 Semantic 象限的事，那不是我们的主推路线——恰恰相反，我们帮客户**避开**不必要的重建模。

**Q8：「逻辑推理你们不做，是不是能力不行？」**
A：这是定位，不是短板。推理引擎是二十年学术积累加标准生态（HermiT/Pellet），自研没有胜算；我们把工程力量押在执行层和治理层——这两个是客户付费意愿最高、且竞争空档最大的位置。对您来说，推理需求走 RDF 标准接口接生态，我们的图层照样消费推理产物（组合模式一）。**不做什么和做什么一样，都是定位的一部分。**

**Q9：「怎么衡量 POC 成功还是失败？」**
A：POC 启动前先定评测口径，事后不吵架：检索型看 faithfulness 提升、citation 准确率、幻觉率下降（vs 纯 RAG 基线）；操作闭环型看状态流转一致性与回滚成功率；治理型看拦截正确率（该拦的拦住、不该拦的放过）和审计完备性。全部跑客户自己的数据，指标不好看我们自己认。

**Q10：「四个问题太简单了，我们的需求很复杂。」**
A：四问是**分诊台**，不是终诊——它只决定「先从哪一象限切入」。复杂需求 = 多象限，正好走组合演进路径：第一步单象限 POC，第二步按痛点叠加（模式二/模式三），第三步才是全栈形态。需求越复杂，越要避免一开始就铺开摊子——这正是决策树存在的意义。
