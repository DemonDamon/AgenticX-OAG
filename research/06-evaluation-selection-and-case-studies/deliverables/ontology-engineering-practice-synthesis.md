# 本体工程实践综合：从语义模型到受控执行

> **文档性质。** 本文将跨方向研究整理为 `AgenticX-OAG` 的工程判断与验收框架，
> 不复述任何受限资料。公开事实以标准、官方文档或已审阅的公开源码为依据；
> 不能被这些来源独立支持的内容一律标为工程建议，并等待 Maintainer 确认。

## 一、结论

本项目不应把“本体”收窄为术语表、图谱 Schema 或检索索引。面向业务闭环时，
它至少涉及四个相互独立但可组合的层次：

| 层次 | 核心问题 | 项目内产物 | 不应承担的职责 | 来源等级 |
|---|---|---|---|---|
| 语义模型 | 系统中有哪些对象、属性、关系和约束？ | `ObjectType`、`Property`、`LinkType`、`Interface`、SHACL 约束 | 不直接决定某个主体能否执行操作 | S1/S2 |
| 执行模型 | 哪个命令可以改变什么状态，失败后如何恢复？ | `ActionType`、前后置条件、状态迁移、副作用、幂等与补偿 | 不接受 LLM 绕过契约直接写存储或外部系统 | S1/S4 |
| 运行时治理 | 谁在什么上下文中可以提议、批准和执行什么？ | 四权矩阵、Harness 四层门禁、审批策略 | 不把检索相关性或语义校验当成授权结果 | S1/S2/S3 |
| 证据与回放 | 为什么做出决定，执行了什么，结果是否符合预期？ | Context Pack、主张、规则命中、审批、Action 事件、结果与审计链 | 不以一段自由文本日志代替结构化证据 | S1/S2/S4 |

这四层的边界应保持明确：语义模型描述业务世界，执行模型定义允许的状态变化，
运行时治理约束提案和操作，证据层负责解释、审计与复现。某一层通过不能推导出
其他层也通过。例如，参数符合 JSON Schema 不代表调用者获得授权；检索到了对象
也不代表 Agent 可以修改该对象。

## 二、项目内核心抽象

| 抽象 | 项目内定义 | 最低契约 | 来源等级 |
|---|---|---|---|
| Object | 有稳定身份、类型和生命周期的业务对象 | 主键、类型、属性、版本、租户、来源 | S1/S2 |
| Property | 对象上有类型、约束和来源的字段 | 数据类型、必填性、约束、敏感级别、来源 | S1/S2/S4 |
| Link | 两类对象之间有方向和语义的关系 | 起止类型、基数、有效期、来源 | S1/S2/S4 |
| Interface | 多类对象共享的能力契约 | 必备属性、允许操作、版本和兼容规则 | S4 |
| Function | 读取对象并计算派生结果的逻辑入口 | 输入输出 Schema、版本、依赖、错误模型 | S1/S4 |
| Action | 改变内部或外部状态的唯一受治理命令入口 | 授权、前后置条件、状态迁移、副作用、幂等、补偿、审计 | S1/S2/S4 |
| Side Effect | Action 在主状态变更之外产生的可观察影响 | 目标系统、重试语义、超时、结果引用、补偿策略 | S4 |

本项目建议把 Function 约束为无外部可观察写入的计算入口，把所有写操作收敛到
Action Gateway。这是 `AgenticX-OAG` 的工程选择（S4），不是对任何公开平台实现的
事实描述。这样可以让读取、提案和执行拥有不同的权限、重试与审计语义。

### Action 最小契约

每个可执行 Action 至少声明以下信息；字段名称以 P07 最终 Schema 为准：

```yaml
action_id: case.assign
version: 1
input_schema: {}
required_permissions: [case.operate]
preconditions: []
state_transition:
  from: [open]
  to: assigned
side_effects: []
idempotency:
  scope: tenant
  key_fields: [case_id, assignee_id, request_id]
postconditions: []
compensation: null
audit:
  event_type: action.executed
  evidence_required: true
```

这里的关键不是字段数量，而是把“允许执行”“执行成功”和“业务结果成立”分开：

1. 授权和前置条件通过后，Action 才能进入执行阶段。
2. 写入或外部调用成功后，仍须验证后置条件。
3. 后置条件失败不等于可以静默重试；系统应按副作用类型选择补偿、人工接管或告警。
4. 同一幂等范围内的重复请求必须返回同一执行引用，不能重复产生副作用。

## 三、Agent 提案进入执行链路

LLM 只负责生成“提案”，确定性的运行时组件负责判断该提案能否继续。建议链路为：

```text
检索 -> 主张 -> 规则求值 -> Agent 提案 -> 四层门禁 -> 授权/审批
     -> Action 执行 -> 后置验证 -> 结果归档 -> 审计回放
```

| 检查点 | 需要回答的问题 | 失败行为 | 来源等级 |
|---|---|---|---|
| 概念层 | 提案中的对象、关系和字段是否属于允许的业务语义？ | 拒绝并返回结构化违规项 | S1/S3 |
| 规则层 | 是否违反 MUST、MUST_NOT 或条件规则？ | BLOCK，不进入工具调用 | S1/S3 |
| 流程层 | 当前状态是否允许该步骤，是否跳过必要审批？ | BLOCK 或转人工审批 | S1/S3/S4 |
| 技能层 | 工具是否在白名单，输入输出是否符合契约？ | BLOCK；禁止临时扩权 | S1/S2/S3 |
| 授权层 | 当前主体是否有对象级操作权或审批权？ | 无 grant 命中时 deny | S1/S2/S3 |
| 执行层 | 前置条件、幂等和副作用策略是否满足？ | 拒绝、返回既有结果或进入受控失败流程 | S1/S4 |

“默认拒绝”只适用于 P09 策略引擎在没有授权 grant 命中时的求值结果，不能扩大为
“任何治理依赖故障都拒绝全部读取”。治理服务不可用时，生产模式至少禁止写操作、
Action 和审批；读操作采用何种策略仍是待确认的运行策略（S4）。显式只读演示模式
可以展示只读数据，但必须显示“治理未接入”，不得伪装为已经通过授权。

## 四、决策事件与回放

审计不应只记录“谁调用了什么”，还要能重建“基于哪些证据和规则，为什么允许或
拒绝，以及执行后发生了什么”。建议每个决策生成稳定的 `decision_id`，并关联：

| 事件阶段 | 必备信息 | 来源等级 |
|---|---|---|
| 检索 | 查询、检索器/索引版本、命中文档或对象、排序分数 | S1/S4 |
| 主张 | 结构化结论、证据引用、置信度、生成模型版本 | S1/S4 |
| 规则 | 规则 ID/版本、输入事实、命中分支、求值结果 | S1/S2/S4 |
| 提案 | 工具/Action、规范化参数、提案主体、会话和租户 | S1/S4 |
| 治理 | 四层门禁结果、权限决策、审批人及策略版本 | S1/S2/S4 |
| 执行 | 幂等键、尝试次数、副作用引用、开始/结束时间 | S1/S4 |
| 结果 | 状态变化、后置条件、补偿或人工接管结果 | S1/S4 |

W3C PROV-O 用于表达实体、活动、主体及其派生关系（S2）；项目字段使用自身 namespace，
不冒充标准词汇。回放必须固定本体、规则、检索和模型版本。若外部副作用不可重复，
回放只能读取已归档结果或运行模拟适配器，不能再次触发真实写入（S4）。

## 五、生产工程质量门

每个 Action 与治理链路至少覆盖以下故障模式。它们应成为 P07-P09 的共享验收矩阵，
而不是只在端到端演示中人工点击一次。

| 场景 | 预期断言 | 最低测试层级 | 来源等级 |
|---|---|---|---|
| 正常路径 | 状态迁移、后置条件、审计事件均成立 | 集成测试 | S1/S4 |
| 权限拒绝 | 无副作用；记录拒绝原因和策略版本 | 单元 + 集成 | S1/S2/S3 |
| 前置条件失败 | Action 未开始，业务状态不变 | 单元测试 | S1/S4 |
| 执行中失败 | 结果明确标为失败或待处理，无“成功”审计 | 集成测试 | S4 |
| 后置条件失败 | 不误报成功；进入补偿或人工接管 | 集成测试 | S4 |
| 补偿失败 | 保留原失败与补偿失败两条事实并告警 | 集成 + 故障注入 | S4 |
| 重试与幂等 | 相同键不产生第二次副作用 | 并发集成测试 | S1/S2/S4 |
| 决策回放 | 固定版本后得到一致规则结果和证据关联 | 回放测试 | S1/S2/S4 |
| 治理依赖故障 | 写操作、Action、审批被阻断；读策略符合明确配置 | 故障注入 | S4 |

上线前还应满足四类横向门槛：

1. **可观测性**：日志、指标和 Trace 共用 `decision_id`、`action_id` 与 `request_id`；
   不在日志中泄露完整敏感字段。
2. **恢复能力**：明确可重试、可补偿、不可逆和必须人工接管的副作用；定期演练恢复。
3. **安全性**：对越权、提示注入、工具参数污染、重放和跨租户访问建立负向用例。
4. **交付性**：Schema、规则和策略均版本化；升级、降级和回滚必须有兼容性说明。

这些是工程建议（S4）。具体 SLO、告警阈值、保留周期和演练频率必须结合部署环境
另行确认，不在研究文档中虚构生产承诺。

| 实践主题 | 现有任务 | 本文补充的验收重点 |

## 七、后续沉淀流程

新增材料或实践经验按以下顺序进入项目：

1. 来源先登记许可、版本、访问时间和可再分发边界。
2. 未复核观察进入对应方向的 `notes/`，不得写成项目能力。
3. 由公开标准、官方资料、公开实现或项目实验独立复核后，才进入 `deliverables/`。
4. 可实施事项登记到 `docs/ontology-evolution-backlog.md`，避免在多个笔记维护状态。
5. 只有任务边界和验收条件稳定后才更新或新增 plan；实现结果以代码、测试和评测为准。
