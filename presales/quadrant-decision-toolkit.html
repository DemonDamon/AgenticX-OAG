一决策树四问 · 售前资格认证

决策树的核心逻辑是逐层排除：先问最具区分度的问题，每一层只做一个二元判断。任一问答「是」即终止并输出象限推荐；四问全「否」落默认兜底（治理层）。第一次客户会议建议现场带着客户一起走。

    决策树全文参照（紫皮书 8.1 × enterprise-landing.md 阶段一 · 第 0 步）

    开始选型
│
Q1 需要逻辑推理吗？（隐含知识派生 / 分类推理）
│   追问：是否需要从已知推导未知？概念间是否存在传递/互斥等逻辑关系？
├─ 是 → Semantic Ontology（知识层）→ 我们只提供 RDF 接口 + 生态合作，不硬上
└─ 否 ↓
Q2 需要多跳关联查询吗？（实体间 N 跳路径发现，> 2 跳）
│   追问：是否需要发现实体间的间接关联？关联路径长度是否 > 2 跳？
├─ 是 → KG Schema（查询层）主打 → 检索型 POC
└─ 否 ↓
Q3 需要操作执行闭环吗？（Action 驱动状态变更 / 审批 / 回滚）
│   追问：是否需要通过操作改变业务对象状态？是否需要审批/回滚？
├─ 是 → Palantir 式执行层主打 → 操作闭环型 POC
└─ 否 ↓
Q4 需要约束 Agent 行为吗？（权限约束 / 行为审计）
├─ 是 → Agent Ontology 治理层主打 → 治理型 POC
└─ 否（四问全否）→ 默认：Agent Ontology 治理层（兜底）

    二四象限结果页 · 定位与打法

    决策树任一分支的落点都在这里。每象限含：核心命题、典型技术栈（紫皮书 7.2 架构栈）、我们的角色映射（卖什么 / 不卖什么 / 走生态接口，取自 enterprise-landing.md §一点五四象定位表）、推荐 POC 类型。一句话定位：AgenticX-OAG = KG Schema（查询层）+ Palantir 式执行层 + Agent Ontology 治理层的三层组合体，Semantic Ontology 走生态接口。

    四组合使用模式

    真实系统很少只用一种本体论。紫皮书 8.3 给出三种经过验证的组合模式——每一种都是「两层各司其职」，不是功能堆叠。

    模式一

    知识层 + 查询层

    Semantic Ontology（知识层）+ KG Schema（查询层）。知识层负责「正确性」，查询层负责「性能」。

    OWL 本体 (TBox) → 推理引擎 HermiT/Pellet → 隐含三元组 ──物化──▶ 图数据库 (Neo4j / NebulaGraph) → Cypher 多跳查询 → 业务系统消费

    知识层定义概念体系与逻辑公理、推理产出隐含三元组；物化进图数据库后供业务系统做高性能多跳查询。

    模式二

    数据层 + 执行层

    KG Schema（数据层）+ Palantir Ontology（执行层）。数据层负责「关联发现」，执行层负责「操作闭环」。

    KG Schema (人/设备/订单图谱) ──映射为强类型 Object──▶ Palantir Ontology (Action + Function) → 处置操作闭环

    典型场景：KG 中发现风险关联后，在 Ontology 中触发处置 Action。对应 AgenticX：检索 → Action Gateway 闭环。

    模式三

    业务层 + 治理层

    Palantir Ontology（业务层）+ Agent Ontology（治理层）。业务层负责「做什么」，治理层负责「能不能做」。

    Agent 发起操作请求 → Palantir Ontology (业务对象 / Action) ──拦截──▶ Agent Ontology (Guardrail 校验) → 允许 / 拒绝

    每次 Agent 调用 Action 前，先过 Guardrail 校验权限和合规性。对应 AgenticX：Harness + 四权矩阵。

    全栈组合（理想形态）

    Semantic → KG Schema → Palantir Ont. → Agent Ont. （知识层） （查询层） （执行层） （治理层）

    注意：理想形态 ≠ 一步到位的目标。见下方演进原则与第五节误区四。

    「组合是演进而来的，不是设计出来的。」

    先用决策树选定一个核心本体论，验证价值后再逐步叠加其他层。在没有验证单一本体论价值前就搭建组合系统，会导致架构复杂度失控、团队认知负荷过重、每一层都做不好。

    —— 紫皮书 8.4 误区四 · 也是 enterprise-landing.md 阶段二的演进原则：POC 验证过的那个象限做深，再按客户实际痛点叠加第二个象限，禁止一上来推三层全栈。
